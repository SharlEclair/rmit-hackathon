# 04 - Technical Architecture

**Purpose.** Fix the technical shape of Assignment Assistant so that any agent can build it without re-deciding the stack. This doc owns the detail for D7, D12, D13, D36-D45 and the enforcement points for C1, C6, C7 and C8.

**Read with.** `AGENTS.md` (constraints) -> `01-DECISIONS.md` (what is settled) -> `05-AI-GUARDRAILS.md` (the policy layer this doc wires in) -> `06-DATA-MODEL.md` (the authoritative schema; table names here are the interface expectation, not the schema of record).

**Status.** No application code exists. Everything below is a specification the first build task implements.

---

## 1. One-paragraph shape

A single Next.js (App Router) deployable serves both the UI and the JSON API. Postgres holds all state and all retrieval state: there is no separate vector database (D38). Every model call goes through one adapter at `src/lib/llm/` (C8, D39), which resolves a configured provider (`deepseek`, `gemini`, or `mock`) at startup and validates the configured model id before serving any request. The guardrail is a pure, network-free layer at `src/lib/guardrail/` (D7) that decides before any model call and post-checks after any model call. Student uploads pass through the same guard as text (C6, D10). Nothing AI-generated reaches a student before tutor approval (C3, D21).

### 2.1 Query layer: Drizzle, explicitly

D37 requires "a typed query layer". That layer is now fixed to **drizzle-orm 0.45.3** with SQL migration files generated by drizzle-kit and committed under `src/lib/db/migrations/`.

Rationale: no code-generation step in the build (nothing can drift between a generated client and the schema), plain SQL migrations a reviewer can read, and TypeScript types inferred from the schema definition.

Prisma is the obvious alternative and is rejected for this MVP on one concrete ground: the npm dist-tags currently disagree. `prisma@8.0.0-rc.19` is a release candidate while `@prisma/client@7.10.0` is stable, so a single `npm i prisma@latest` produces a mixed major line inside a 48-hour build. If Prisma is ever preferred, pin **both** packages to the same 7.x stable version and regenerate migrations - never a `latest` tag, never an rc. This narrows D37 rather than changing it; no other doc depends on the ORM choice.

### 2.3 Runtime, local prerequisites, and the deployment constraint

Verified on the authoring machine: Node v24.15.0, npm 11.12.1, pnpm available, Python 3.13.2, uv available, git available. Docker CLI and Docker Compose v5.1.4 are installed **but the Docker daemon is not running**, so a compose-provided Postgres is a "start Docker Desktop first" step. Postgres is not installed locally and nothing is listening on 127.0.0.1:5432. `psql`, `gh`, `vercel` and `wrangler` are not installed.

Consequences for the build:

1. Local Postgres is a prerequisite step, not an assumption. Either start Docker Desktop and bring up the compose Postgres, or point `DATABASE_URL` at a hosted Postgres (Neon, Supabase). The first build task should treat this as a documented setup step, not a discovery.
2. The app must not depend on `psql`. Migrations run through `pnpm db:migrate` (drizzle-kit); no shell tool is required.
3. `gh`, `vercel` and `wrangler` are absent, so the deploy path must not require them. Use a container/VPS-style target or a Git-based deploy.

**Deployment constraint (D41 vs serverless).** The default `local` storage driver writes to `STORAGE_LOCAL_DIR` on the machine running the server. That is incompatible with serverless filesystem semantics (Vercel functions, for example): a file written during one invocation is not guaranteed to exist in the next. Resolve it one of two ways, and state which one before deploying:

| Host shape | Requirement |
|---|---|
| Long-lived Node server (container, VPS, Render-style service) - **recommended for the demo** | Keep `STORAGE_DRIVER=local` and mount a persistent volume for `STORAGE_LOCAL_DIR`. D41 holds as written and the demo path is unchanged. |
| Serverless host | Set `STORAGE_DRIVER=s3` and supply `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`. No code change is needed because the driver sits behind the interface (section 8). |

A deployment that runs the `local` driver on a serverless host is a defect: uploads disappear between invocations and the symptom surfaces during judging. `12-OPERATIONS.md` owns the deployment runbook; it must carry this same constraint.

## 5. The provider adapter

### 5.1 Why it exists

Provider choice was never finalised upstream (handoff 61.6), and the architecture must not depend on it (D39). The adapter is also the single place where model ids, retries, timeouts, budget accounting and prompt-cache-friendly request assembly are handled, so those behaviours are testable once instead of per call site.

### 5.2 The interface (exact)

```ts
// app/src/lib/llm/types.ts

export type LlmProviderId = 'deepseek' | 'gemini' | 'mock';

export type AiCapability =
  | 'assignment_analyst'
  | 'policy_guard'
  | 'student_assistant'
  | 'discussion_moderator'
  | 'insight_engine';

export type LlmRole = 'system' | 'user' | 'assistant';

export interface LlmTextPart { type: 'text'; text: string }
export interface LlmImagePart { type: 'image'; mimeType: string; dataBase64: string }
export interface LlmAudioPart { type: 'audio'; mimeType: string; dataBase64: string }
export interface LlmVideoPart { type: 'video'; mimeType: string; dataBase64: string }
export interface LlmDocumentPart {
  type: 'document';
  mimeType: string;
  dataBase64: string;
  name: string;
}
export type LlmContentPart =
  | LlmTextPart | LlmImagePart | LlmAudioPart | LlmVideoPart | LlmDocumentPart;

export interface LlmMessage { role: LlmRole; content: LlmContentPart[] }

export interface JsonSchema { [key: string]: unknown }

export interface LlmToolDefinition {
  name: string;
  description: string;
  parameters: JsonSchema;
}

export interface LlmResponseFormat {
  type: 'json_schema';
  name: string;              // stable schema name, e.g. 'guardrail_decision'
  schema: JsonSchema;
  strict: true;
}

export interface LlmRequest {
  capability: AiCapability;
  /** Resolved from env at startup and validated there. Never a literal at a call site. */
  modelId: string;
  /** Stable id of the unchanging prompt prefix. Part of the cache key and the audit log. */
  systemPrefixId: string;
  /** Static prefix first, variable content last. See 5.5. */
  messages: LlmMessage[];
  responseFormat: LlmResponseFormat | { type: 'text' };
  tools?: LlmToolDefinition[];
  temperature: number;        // 0 for every classifying capability
  maxOutputTokens: number;
  timeoutMs: number;
  /** Budget accounting unit. One assistant session, one ingestion run, one moderation batch. */
  sessionId: string;
}

export interface LlmToolCall { id: string; name: string; argumentsJson: string }

export interface LlmUsage {
  inputTokens: number;
  cachedInputTokens: number;  // cache hits; must be reported by the provider or 0
  outputTokens: number;
}

export interface LlmResponse {
  provider: LlmProviderId;
  modelId: string;
  /** Parsed JSON when responseFormat is json_schema; otherwise null. Untrusted until validated. */
  json: unknown | null;
  text: string | null;
  toolCalls: LlmToolCall[];
  usage: LlmUsage;
  finishReason: 'stop' | 'length' | 'tool_calls' | 'content_filter';
  latencyMs: number;
  providerRequestId: string | null;
}

export interface LlmCapabilities {
  jsonOutput: boolean;
  toolCalls: boolean;
  vision: boolean;
  audio: boolean;
  video: boolean;
}

export interface ModelValidationResult {
  ok: boolean;
  provider: LlmProviderId;
  modelId: string;
  checkedAt: string;          // ISO 8601
  errorCode?: LlmErrorCode;
  reason?: string;
  latencyMs: number;
}

export interface LlmProvider {
  readonly id: LlmProviderId;
  readonly capabilities: LlmCapabilities;
  /** Startup only. Must be called once per process before any request is served. See 5.4. */
  validateConfiguration(): Promise<ModelValidationResult>;
  complete(request: LlmRequest): Promise<LlmResponse>;
}

export type LlmErrorCode =
  | 'CONFIG_INVALID'
  | 'MODEL_UNKNOWN'
  | 'AUTH_FAILED'
  | 'RATE_LIMITED'
  | 'TIMEOUT'
  | 'PROVIDER_UNAVAILABLE'
  | 'SCHEMA_INVALID'
  | 'BUDGET_EXCEEDED'
  | 'CONTENT_FILTERED';

export class LlmError extends Error {
  readonly code: LlmErrorCode;
  readonly retryable: boolean;
  constructor(code: LlmErrorCode, message: string, retryable: boolean);
}
```

`resolveProvider()` reads `LLM_PROVIDER` and returns the matching `LlmProvider`. Everything above it in the stack depends only on this interface (and on `JsonSchema`), never on a vendor type.

### 5.3 Default provider: DeepSeek

| Fact | Value |
|---|---|
| Provider id | `deepseek` |
| Default model id | `deepseek-flash` (DeepSeek-V4.1-Flash) |
| Other accepted model id | `deepseek-v4-pro` - a valid value for `LLM_MODEL_REASONING`, not the default |
| Base URL | `https://api.deepseek.com`, OpenAI-compatible surface |
| Context window | 1,000,000 tokens |
| Structured output | JSON output supported |
| Tool calls | Supported |
| Vision | Supported, so the same model covers image-bearing student uploads |
| Prompt caching | Supported. Cache-hit input tokens are billed far below cache-miss input tokens. |

Consequences the build must honour:

- **One model covers all five capabilities.** `LLM_MODEL_REASONING` and `LLM_MODEL_MULTIMODAL` both resolve to `deepseek-flash` when `LLM_MODEL_MULTIMODAL` is empty.
- **Attachment resolution uses the same rule.** With the shipped modalities (PNG/JPEG, PDF, plain text - O11), image and PDF extraction resolves `modelId` from `LLM_MODEL_MULTIMODAL` if non-empty, else `LLM_MODEL_REASONING`. The env default is empty, so extraction and generation both run on `deepseek-flash`; a non-empty `LLM_MODEL_MULTIMODAL` is an override for cost or capability reasons, not a requirement. Audio and video never reach this resolution because the picker refuses them.
- **The two known-good ids are `deepseek-flash` and `deepseek-v4-pro`.** Configure one of them in `LLM_MODEL_REASONING`. There is no automatic fallback between them: the adapter never silently switches model ids, because a silent switch changes the prompt-cache prefix behaviour, the cost profile, and the behaviour under test. If the configured id fails, that is a loud startup failure (5.4), not a fallback.
- **Model ids are never invented or composed.** The id string comes from `LLM_MODEL_REASONING` (or `LLM_MODEL_MULTIMODAL` when set) and is passed through unchanged. Do not append date suffixes, aliases, or `-latest`.
- **A 1M window is not a licence to send everything.** Retrieval still selects the smallest sufficient set of T1-T3 source chunks (section 6). Context is a cost and an accuracy risk, not a feature.

### 5.4 Startup validation: fail loudly, never at the first student message

An unknown or unavailable model id returns HTTP 400 from the provider. If that is discovered on the first student message, the failure lands in the demo, in front of a judge, attributed to the assistant rather than to configuration. It is therefore a **startup** failure.

Procedure, run once per process before the server accepts a request:

1. Read `LLM_PROVIDER`. Missing or not one of `deepseek` | `gemini` | `mock` -> `CONFIG_INVALID`, abort.
2. For `deepseek` and `gemini`, require the matching key (`DEEPSEEK_API_KEY`, `GEMINI_API_KEY`) to be non-empty -> else `CONFIG_INVALID`, abort.
3. Resolve `modelId` from `LLM_MODEL_MULTIMODAL` if non-empty, else `LLM_MODEL_REASONING`.
4. Issue one minimal probe completion with that `modelId`: one short input token, `max_tokens: 1`, no tools.
5. Map the outcome:

| Provider signal | Code | Retry | Startup behaviour |
|---|---|---|---|
| HTTP 200 | - | - | Continue. Log provider, model id, latency. |
| HTTP 400 (invalid/unknown model id) | `MODEL_UNKNOWN` | No | **Abort.** Print the configured id and the provider message. |
| HTTP 401 / 403 | `AUTH_FAILED` | No | **Abort.** Never print the key. |
| HTTP 429 | `RATE_LIMITED` | Once, 1s jittered | Abort if the retry also fails. |
| HTTP 5xx | `PROVIDER_UNAVAILABLE` | Once, 1s jittered | Abort if the retry also fails. |
| Timeout (> 10s) | `TIMEOUT` | No | **Abort.** |

6. `LLM_PROVIDER=mock` skips the network probe entirely. The mock provider's `validateConfiguration()` returns `ok: true` for the `mock` model id and for `deepseek-flash`, so the demo path and the test path share one code path.

**Abort means abort.** The process exits non-zero (exit code 78, `EX_CONFIG`) with a one-line, secret-free message on stderr. There is no degraded mode in which the assistant answers without a validated model, because a degraded assistant is an unguarded assistant. Any test or dev-server wrapper that would swallow this exit code is a defect.

The same fail-loud rule applies to schema state: `pnpm start` verifies that the applied migration head equals the repository migration head and aborts with the same exit code if it does not.

### 5.5 Prompt assembly and prompt caching

Cache-hit input tokens are much cheaper than cache-miss input tokens, and a cache hit requires an **identical prefix**. Prompt assembly is therefore ordered once, in one module, and every capability uses it. Stable content first, variable content last, and nothing that changes per turn is allowed above the variable boundary.

```text
[ A. STATIC PLATFORM BLOCK ]              identical for every request, forever
    - academic integrity constraints (C1)
    - capability role and refusal obligations
    - output contract instructions
    - systemPrefixId + prompt version, e.g. "guardrail-v3"

[ B. STATIC ASSIGNMENT POLICY BLOCK ]     identical for every request in one assignment
    - approved AI Usage Policy (JSON), rendered deterministically
    - approved milestone/checklist titles (ids and titles only)

[ C. SEMI-STATIC GROUNDING BLOCK ]        changes only when sources or approvals change
    - retrieved T1-T3 source chunks with ids, page anchors, verbatim text

[ D. VARIABLE BLOCK ]                     changes every turn, must be last
    - student context: current milestone, checklist state, prior tutor replies
    - conversation history
    - the current student turn, including any extracted upload text
```

Rules:

1. Blocks A and B are byte-identical across requests in the same scope. Rendering them from a Map with insertion order, not from object spread, so key order cannot drift between processes.
2. Nothing derived from student input may appear in block A or B. This is both a cache rule and a control: a student cannot influence the static policy prefix.
3. `systemPrefixId` changes whenever block A or B changes, in the form `<capability>-v<n>`. A prefix change requires re-running the guardrail golden set (05 section 11).
4. The adapter reports `usage.cachedInputTokens`; the decision log records it (section 10) so cache effectiveness is visible rather than assumed.
5. Do not exceed the 1M window "because it is available" - a bigger context is a slower, more expensive, less precise request.

### 5.6 Budget accounting

`LLM_MAX_CALLS_PER_SESSION` (default `12`) is a hard ceiling on model calls per `sessionId`. The counter increments before the call is issued, is held in Postgres so it survives a restart, and on exhaustion the adapter throws `BUDGET_EXCEEDED`. That error is **not** retryable and the assistant treats it as a refusal-equivalent: the student sees a plain "the assistant is unavailable right now" state, the guardrail decision is logged, and the failure is loud in the server log. A runaway loop must fail loudly rather than burn budget silently.

### 5.7 Error handling, retries, timeouts

| Failure | Retry policy | What the student or tutor sees |
|---|---|---|
| Provider 4xx config/model (`MODEL_UNKNOWN`, `AUTH_FAILED`) | Never | Assistant unavailable; operator error in the log. Startup validation should have made this impossible. |
| Schema validation of model output fails | **Never** (D16, AGENTS.md 6.4) | The response is converted to a `REFUSE` verdict with rule `SYS_SCHEMA_INVALID`. Retrying until the model complies is forbidden. |
| 429 / 5xx / timeout | At most one retry, jittered; never after tokens have been produced | On second failure, refusal-equivalent. |
| `CONTENT_FILTERED` from the provider | Never | Refusal-equivalent; the guardrail logs its own rule, not the provider's. |
| `BUDGET_EXCEEDED` | Never | Assistant unavailable state. |

**Streaming is excluded from the MVP.** A streamed response is displayed before it is validated, which makes the schema-validated contract unenforceable and the post-check (05 section 3.2.3) too late. The assistant returns one complete, validated payload.

### 5.8 The `mock` provider (required)

`LLM_PROVIDER=mock` is a first-class mode, not a test stub bolted on. Requirements:

1. **Offline and deterministic.** No network. Same input, same output, byte for byte, across processes and machines.
2. **Same interface, same types.** The mock implements `LlmProvider` exactly; no capability may special-case it.
3. **Fixture-driven.** Responses are keyed by a hash of `(capability, systemPrefixId, canonicalised request body)`. Unknown keys return a deterministic refusal-shaped response, never an invented success.
4. **Whole loop walkable.** With `mock`, a tutor can upload a document, the Analyst can produce candidates, the tutor can approve them, a student can send a message, receive an allowed answer, and receive a refusal for a prohibited request. All four capabilities, no key.
5. **Golden-set capable.** The mock can be forced to return a valid `guardrail_decision` for any requested verdict so the golden set exercises the model-enhanced path (05 section 11.4).
6. **Identity of last resort.** The demo runs on `deepseek`; `mock` is the fallback when the network is hostile. Switching is one environment variable and no code change.

### 5.9 Enforcing C8 (no vendor SDK outside `src/lib/llm/`)

Two checks, both required:

1. ESLint `no-restricted-imports` at the repository root, forbidding `openai`, `@google/genai`, `@google/generative-ai`, `@anthropic-ai/sdk` and any provider hostname in import paths outside `src/lib/llm/**` (illustrative shape, not application code):

```jsonc
// app/.eslintrc.json (excerpt)
{
  "rules": {
    "no-restricted-imports": ["error", {
      "patterns": [
        { "group": ["openai*", "@google/genai*", "@anthropic-ai/*"],
          "message": "C8: vendor SDKs may only be imported inside src/lib/llm/." }

  },
  "overrides": [
    { "files": ["src/lib/llm/**"], "rules": { "no-restricted-imports": "off" } }
```

2. A CI grep gate that fails if any file outside `src/lib/llm/` contains `api.deepseek.com`, `generativelanguage.googleapis.com`, or `Authorization: Bearer`. Grep is a backstop for the failure mode ESLint misses: a raw `fetch` to the provider.

## 6. Data, retrieval and the absence of a vector database

### 6.1 Retrieval state (logical)

Owned physically by `06-DATA-MODEL.md`. The retrieval interface depends on these fields existing:

| Field group | Fields | Why |
|---|---|---|
| Chunk identity | `id`, `assignment_id`, `source_id` | Provenance (D15) and citation. |
| Location | `chunk_index`, `page_from`, `page_to`, `section_label` | Page-mapped deep links (D43). |
| Text | `text`, `char_count` | Display and prompt assembly. |
| Index | `tsv` (generated `tsvector`) | FTS. GIN index. |
| Tier | derived, not stored: `assignment_sources.kind` maps to `T1`; approved `faq_entries` and published `ai_policy_rules` are `T2`; approved `milestones` and `checklist_items` are `T3` | Truth hierarchy (D14, 15-GLOSSARY section 3). |

### 6.2 Chunking

1. Split on document structure first: heading boundaries, then paragraph boundaries, then sentence boundaries. Never split inside a table row or a numbered requirement.
2. Target 700 tokens per chunk, 120-token overlap between adjacent chunks; `char_count` is the stored measure.
3. Every chunk keeps `page_from`/`page_to` and `section_label` so a citation can be rendered as "page 4" and highlighted in the viewer.
4. Chunks are immutable once written. Re-ingesting a changed document creates a new revision and new chunk ids; it never mutates existing chunks, because published AI artifacts cite chunk ids (D15).

### 6.3 Query and ranking

```text
1. Build tsquery from the student turn: websearch_to_tsquery('english', normalised_turn)
2. Filter: assignment_id = current, and the source kind is T1, or the row is an approved
   T2/T3 artifact (see the tier row in 6.1)
   - T4 (discussion_threads, discussion_posts) and T5 (unapproved artifacts) are never
     grounding (D14, O10)
3. Rank: ts_rank_cd(tsv, tsquery) * tier_weight
   - tier_weight: T1 = 1.00, T2 = 0.90, T3 = 0.70
4. Threshold: keep chunks with adjusted score >= MIN_CHUNK_SCORE (0.05)
5. Cap: top 8 chunks, at most 3 per source document (diversity guard)
6. Return: SourceChunk[] with id, document id, page range, verbatim text, tier
```

### 6.4 Retrieval failure is a first-class outcome

If step 4 yields zero chunks, the assistant must not answer from general knowledge. It returns the sanctioned phrase from 15-GLOSSARY section 2:

> "We could not find this in your assignment documents"

and offers the two real options: rephrase, or ask the tutor privately (which creates a Query). The wording may evolve; the behaviour may not. An empty retrieval set that produces a confident general-knowledge answer is a C2 violation, because a model answer about this assignment is a fabricated requirement.

### 6.5 The optional embedding upgrade, and its hard boundary

D38 permits embeddings later **through the same interface**:

```ts
export interface RetrievalStrategy {
  readonly id: 'fts' | 'hybrid';
  retrieve(input: {
    assignmentId: string;
    queryText: string;
    allowedTiers: ReadonlyArray<'T1' | 'T2' | 'T3'>;
    maxChunks: number;
  }): Promise<SourceChunk[]>;
}
```

`fts` is the only implementation in the MVP. A `hybrid` implementation may use `pgvector` in the same Postgres instance. It may not introduce a second datastore, a second deployable, or a second source of truth for chunks.

## 7. Ingestion pipeline (Assignment Analyst)

Orchestrated by `src/features/assignment/`. One ingestion run per document set revision. Every stage is retryable and idempotent on `(content_hash, prompt_version)`.

| # | Stage | Input | Output | Failure behaviour |
|---|---|---|---|---|
| S0 | Accept | Tutor upload of one or more files | Upload manifest | Per-file validation errors shown inline; the run does not start. |
| S1 | Validate | File bytes, declared mime | Accepted or rejected | Reject with a clear message on: unsupported type, size > `UPLOAD_MAX_BYTES`, or mime mismatch against content sniffing. Never silently skip or silently convert. Tutor set (O5, **D57**): PDF, DOCX, PPTX, PNG/JPEG, plus plain text and Markdown. Shipped student set (O11): PNG/JPEG, PDF, plain text. Student audio (MP3/WAV) and video (MP4) are refused **at the picker** with rule `UP5`, before this stage runs - they are never stored and never extracted. |
| S2 | Store original | Accepted bytes | Object in the storage driver + `assignment_sources` row | Immutable. `content_hash` (SHA-256) recorded. Identical hash + same assignment = reuse, no duplicate row. |
| S3 | Extract | Stored object | Plain text + a page/offset map | PDF text layer; DOCX/PPTX XML text; image -> vision transcription via the adapter. Scanned PDF with no text layer is flagged for tutor attention rather than guessed. |
| S4 | Normalise | Extracted text | Canonical text + page anchors | Unicode NFC; collapse whitespace; de-hyphenate line-break splits; preserve paragraph and heading boundaries; preserve page anchors (D43). |
| S5 | Chunk and index | Canonical text | `source_chunks` rows with `search_tsv` | Section 6.2. Re-running S5 for the same hash is a no-op. |
| S6 | Analyst passes | Chunks (T1) | Candidate artifacts | **Five separate passes, not one mega-prompt**: (a) structure + requirements, (b) milestones + checklist items, (c) FAQ candidates, (d) AI Usage Policy, (e) ambiguity/contradiction findings. Separate passes make each independently testable and independently re-runnable. |
| S7 | Schema validation | Model output | Validated candidate or a hard failure | A candidate that fails its JSON schema moves to `REJECTED` with the schema error recorded. It is never partially persisted and never published (D16). |
| S8 | Persist with provenance | Validated candidates | Rows with `provenance` and `publicationStatus = NEEDS_REVIEW` | `provenance` = model id, prompt version, `groundingChunkIds`, generation timestamp. Status starts at `AI_GENERATED` and immediately moves to `NEEDS_REVIEW`. |
| S9 | Tutor review | Candidates | Edits, rejects, approves | UI shows every candidate with the badge `AI generated - requires tutor approval` (C3). Discarded candidates move to `REJECTED` and are retained for audit. |
| S10 | Publish | Approved artifacts | Student-visible content | `APPROVED -> PUBLISHED`. Only this transition makes anything student-visible (D21, D22). |

Constraints on S6:

- The Analyst may propose **structure and navigation**, never requirement wording as authoritative (C2, D17). Requirement records are stored verbatim from the source with a page anchor; the Analyst's job is to identify and locate them, not to rewrite them.
- The Analyst may not produce checklist items above the planning-level ceiling (D20, O1). Enforcement is specified in 05 section 6.3.
- Ambiguity detection **detects and locates**, it does not author a clarification (D23). Output is `{finding, sourceChunkIds, whyItIsAmbiguous}`; the tutor writes the clarification.
- The Analyst never runs on student uploads. Student uploads take the separate path in section 9.2 step 12 and are never indexed as assignment sources.

## 9. Auth, authorisation and per-screen data flow

### 9.1 Auth (D42)

| Concern | Specification |
|---|---|
| Registration | Email + password. Password hashed with a memory-hard KDF (argon2id preferred; bcrypt cost >= 12 acceptable). No email verification. |
| Session | Opaque random session id in an `httpOnly`, `Secure` (in non-local environments), `SameSite=Lax` cookie. Server-side session row with expiry and revocation. Signed with `AUTH_SECRET`. |
| Role claim | `role: 'tutor' | 'student'` on the session and on the user row. Resolved server-side on every request; never trusted from the client. |
| Route protection | A server-side guard per route group. Route handlers repeat the check; a layout-level check is convenience, not authorisation. |
| Enrolment scope | A student may only reach assignments for courses they are enrolled in; a tutor only for courses they teach. Every assignment-scoped query filters on that scope in SQL, not in the UI. |
| C4 / D26 | Tutor-facing queries never select student identity for anonymous posts. There is no API that accepts an anonymous post id and returns an author id. See 05 section 9. |
| C7 | `AUTH_SECRET`, `ANON_ID_SECRET`, API keys, and `CANVAS_*` values are read once into a server-only config module, never serialised into a response, and never logged. |

### 9.2 The assistant request path (the path that matters most)

```text
 1. Client POST /api/assignments/:id/assistant/messages
      body: { text, uploadIds[] , clientTurnId }
 2. Auth + enrolment scope check. Reject 401/403. (No model call.)
 3. Load the approved AI Usage Policy for this assignment (T2). Absent or
    APPROVED-less policy => REFUSE with rule POLICY_ABSENT. (No model call.)
 4. GUARDRAIL PREFLIGHT - src/lib/guardrail, pure, no network (D7):
      L0 normalise -> L1 deterministic rules -> L2 policy overlay -> L3 scope
      If verdict is REFUSE / ESCALATE_TO_TUTOR / CLARIFY, persist the decision,
      render the matching response template, and RETURN. No model call.
 5. Retrieval (section 6.3) with tiers T1-T3.
 6. Prompt assembly (section 5.5): static prefix, then policy, then chunks,
      then student context, then history, then the current turn LAST.
 7. Adapter call with responseFormat = json_schema (assistant_response).
      Budget check first; BUDGET_EXCEEDED is terminal (5.6).
 8. Validate against the schema. Validation failure => REFUSE
      rule SYS_SCHEMA_INVALID. Never retry (D16).
 9. GUARDRAIL POST-CHECK - deterministic, on the produced text:
      code-block / solution-shape detection, requirement-paraphrase check,
      scope check, forbidden-verb check for checklist-like output.
      A tripped post-check replaces the response with the refusal template.
10. Persist the assistant message with provenance: model id, systemPrefixId,
      groundingChunkIds, guardrail decision id, usage, latency.
11. Log the decision fields (section 10). Never log student content.
12. Attachments: the request contract accepts text plus optional attachment ids whose
      stored objects are the shipped modalities - PNG/JPEG, PDF, and plain text (O11).
      Extraction runs BEFORE step 4 in the same request; the extracted content
      (vision/OCR text for an image, the text layer for a PDF, the text itself) is
      inserted as student content and re-enters the guard at step 4. An upload is
      input to understanding, never a request to perform work (C6, D10).
      Audio (MP3/WAV) and video (MP4) never reach the adapter: the upload endpoint
      refuses them at the picker with rule UP5, before storage and before the guard,
      so there is no transcription path to guard. Pasted code or a pasted error
      message is the text modality and is covered by the same guard unchanged.
13. Return: { messageId, text, policyNote, citations[], decisionId }.
```

Steps 4, 8 and 9 are the guardrail. None of them may be reordered, skipped, or made optional by a feature flag.

## 10. Cross-cutting concerns

### 10.1 Logging

| Log | Contains | Must not contain |
|---|---|---|
| Guardrail decision log | decision id, assignment id, capability, verdict, rule ids, `systemPrefixId`, model id, latency, usage tokens (incl. cached), timestamp, anon session reference | student text, upload bytes, extracted upload text, file names, email addresses, keys, cookies |
| Ingestion run log | run id, stage, document hash, chunk count, prompt version, model id, usage | document text, tutor identity in message bodies |
| Application error log | error code, stack, route, request id | request bodies, headers carrying credentials |

The guardrail decision log is the audit artifact for D15 and the subject of 05 section 8. Its column list is the contract; adding a column that holds student content requires an explicit decision-register entry.

### 10.2 Caching

Only two caches in the MVP. (a) Prompt caching at the provider, achieved by prefix stability (5.5). (b) HTTP caching of the Assignment Health aggregate payload for 60 seconds, keyed by `(assignmentId, window, viewerScope)`. No result cache keyed by student input, because a cache key derived from student text is a place for a prohibited answer to be replayed to a different student.

### 10.3 Testing strategy

| Layer | Test type | Tooling | Rule |
|---|---|---|---|
| Guardrail | Unit, no network | `tests/guardrail/golden-set.test.ts` against the golden set in 05 section 11 | Deterministic cases must pass with the model disabled entirely. This is the primary regression gate. |
| Adapter | Contract tests against `mock` | `tests/llm/` | Every capability exercised through the same interface; error mapping asserted per row of 5.7. |
| Ingestion | Fixture documents -> chunks -> candidates | `tests/` | Schema-valid output for each of the five passes; S7 failure goes to `REJECTED`, never partial. |
| Retrieval | Fixture chunks + queries | `tests/` | Tier filter excludes T4/T5; zero-chunk path returns the sanctioned message. |
| Analytics | Fixture cohort | `tests/analytics/` | Suppression, complementary suppression and the difficulty rule, per `08-ANALYTICS-SPEC.md`. |
| Auth | Route-level | `tests/` | A student cannot read another student's queries; no API returns an anonymous author id. |

## 12. Failure modes the architecture is designed around

| Failure | Design response |
|---|---|
| Unknown model id discovered mid-demo | Startup probe aborts the process (5.4). |
| Provider down or rate limited during judging | One retry, then refusal-equivalent; `LLM_PROVIDER=mock` switches the whole loop offline with no code change (5.8). |
| Model returns malformed JSON | Refusal, never a retry loop, never a partially rendered answer (D16). |
| Model returns a plausible but prohibited answer | Deterministic post-check replaces it with the refusal template (9.2 step 9). |
| Student tries to launder a prohibited request through an upload | Same guard, all shipped modalities; the attachment is extracted and re-fed as student content (C6, D10, O11). Images, PDF, and plain text ship, so `UP1`-`UP4` are live paths. Audio and video are refused at the picker with `UP5` and never reach extraction; that refusal comes from the modality, not from a content judgement, so enabling the modality later cannot silently ship a more permissive path. |
| Retrieval finds nothing | Sanctioned "we could not find this in your assignment documents" message; no general-knowledge answer (6.4). |
| Unknown Postgres state at deploy | Migration head mismatch aborts startup (5.4). |
| Demo network hostile | `mock` provider plus local storage driver: no external dependency in the critical path. |
| Tutor skips review to save time | Impossible by construction: only the `APPROVED -> PUBLISHED` transition is student-visible (D21). |

## 13. Open questions this doc does not settle

Recorded rather than guessed, per AGENTS.md 4.1.4.

1. **Where ingestion runs.** RESOLVED by **D60**: a Postgres-backed job row polled by the ingestion state screen. Stage S6 needs several model calls that can exceed a request timeout, and the job row needs no new service while surviving a page reload. The route handler only enqueues and returns.
2. **Extraction for scanned PDFs.** Vision transcription is specified (S3) but its confidence handling is not. Working default: mark the document `needs_tutor_attention` and do not chunk it.
3. **Whether the Assignment Map is stored as nodes, edges, or both.** `06-DATA-MODEL.md` section 7.2.4-7.2.6 owns the answer (`assignment_structures`, `requirement_nodes`, and the Map edge tables); this doc only requires that a node can deep-link to a page.
4. **`insight_engine` model calls.** The topic-grouping pass (see `08-ANALYTICS-SPEC.md` section 7) may need an adapter call. If it does, its budget is counted per analytics refresh, not per student session; the exact accounting is unsettled.
5. **Cost ceiling per ingestion run.** `LLM_MAX_CALLS_PER_SESSION` is per session; an ingestion run has its own budget. Working default: 5 passes x 1 call, 2 retries total across the run.
